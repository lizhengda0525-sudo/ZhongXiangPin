# Mock 与并行开发策略

## 目标

让前端和后端可以并行推进，同时避免 Mock 数据与真实契约漂移。

## 单一事实源

`docs/plan/openapi.yaml` 是所有 Mock 请求和响应形状的单一事实源。`deploy/migration/V1__init_schema.sql` 和后续 migration 是种子数据、状态持久化和交易事实的单一事实源。

M1 可以补齐 OpenAPI examples 和前端内存 Mock 的数据形状，但不创建后端 Java 代码。M2 可以补齐 migration 和种子数据约束，但不创建 Mapper、Repository 或业务实现。后续 Mock 数据可以放在前端源码中，但示例必须来自 OpenAPI，或至少手工校验过与 OpenAPI 一致。

## Mock 层级

| 层级 | 使用时机 | 规则 |
| --- | --- | --- |
| OpenAPI 示例 | 契约和文档任务 | 每个端点应包含成功示例和代表性失败示例。 |
| 前端内存 Mock | 后端端点尚未实现 | 必须使用和真实 API 调用相同的 TypeScript 类型。 |
| 后端本地 Mock 端点 | M3 后端工程存在后，外部依赖不存在，例如支付回调 | 只能在 local profile 启用。 |
| 种子数据 | 后端联调和演示 | 必须通过 migration 或 seed 脚本写入，不依赖手工点库。 |

## 必要 Mock 场景

### 认证

- 注册成功。
- 用户名重复。
- 密码登录成功。
- 密码错误。
- 登录过期。
- 非管理员访问后台端点。

### 会场

- 正常活动。
- 活动未开始。
- 活动已结束。
- 活动已禁用。
- 标签命中。
- 标签未命中。
- 无可参团队伍。
- 缓存未命中后回填。

### 交易

- 开团锁单成功。
- 参团锁单成功。
- 重复 `clientOrderNo`。
- 队伍已满。
- Mock 支付成功。
- 重复 `payNo`。
- 退款成功。
- 重复 `refundNo`。

### 运行态

- 未支付订单超时关闭。
- 过期未成团队伍退款。
- 失败可靠事件重试。
- Redis 运行态丢失并从 MySQL 重建。

### 后台

- 活动更新成功/失败。
- 标签任务执行成功/失败。
- 后台订单退款成功/重复。
- 任务重试成功/失败。
- DCC 非法值被拒绝。
- 线程池非法值被拒绝。

## 前端 Mock 契约规则

- Mock 函数返回 `Promise<ApiResponse<T>>`，或返回与真实客户端封装一致的解包类型。
- Mock 状态字符串必须来自集中枚举或类型定义。
- Mock ID 要稳定且可读，例如 `ORD-MOCK-001`。
- Mock 时间值使用 ISO-8601 字符串。
- 不要只在 Mock 里编码业务规则。如果 Mock 需要某条规则，后端 SDD 必须描述同一条规则。

## 后端本地 Mock 规则

- 支付模拟可以是 local-only。
- Debug 端点只允许在 `local` profile 注册。
- 本地 Mock 响应仍必须使用 `ApiResponse`。
- Mock 端点不能在生产路径绕过归属校验、状态机或幂等检查。

## 契约更新检查清单

当前端页面需要新数据时：

1. 在 `openapi.yaml` 中新增或更新 schema。
2. 增加成功和失败示例。
3. 如果改变行为，更新对应 SDD；后端实现细节只在 M3 之后落地。
4. 如果改变页面状态，更新前端 SDD。
5. 更新 Mock fixture。
6. 如果改变数据事实源，更新 migration 或下一版 migration，并同步契约对齐映射。
7. 条件具备时运行 OpenAPI lint 和前端类型检查。

## 完成标准

- 每个 P0 基础功能端点都有成功示例和至少一个相关失败示例。
- 用户端和管理端可以在后端未完成前基于 Mock 数据运行。
- 从 Mock 切换到真实 HTTP 不需要重写页面逻辑。
