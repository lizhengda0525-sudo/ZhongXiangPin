# 项目开发规范

## 1. 规范定位

本文是众享拼项目的编码规范入口，所有后端 Java 开发任务默认遵守本文。本文不替代架构、业务、SDD、OpenAPI 和 Harness 文档，而是规定实现代码时必须遵守的工程质量底线。

后端 Java 代码以《阿里巴巴 Java 开发手册》和 P3C 规约插件为基准。当前可参考的公开基线是 Alibaba P3C GitHub 仓库中的《Java 开发手册（黄山版）》和规约插件说明：

- [Alibaba P3C GitHub](https://github.com/alibaba/p3c)
- [P3C 在线说明](https://alibaba.github.io/p3c/)

如果后续官方手册版本更新，项目优先按最新稳定公开版本升级，但升级前必须记录影响范围，避免一次性引入大量无关格式化变更。

## 2. 适用范围

本文适用于：

- `backend/**/*.java`
- `backend/**/resources/**/*.xml`
- `deploy/migration/**/*.sql`
- 后端相关测试代码
- 后端构建、CI、静态扫描和质量门禁

前端代码继续遵守本项目 TypeScript、Vue、OpenAPI 类型一致性和 UI 规范。当前文档中的注释原则同样适用于前端复杂业务逻辑，但 Java 规约条款只约束后端。

## 3. 总体原则

- 每次实现任务都必须先确认本文是否影响当前代码。
- 新增 Java 代码默认按阿里巴巴 Java 开发手册的命名、常量、集合、并发、异常、日志、单元测试、安全、MySQL 和工程结构规范执行。
- 所有文本文件统一使用 UTF-8 编码；除 Windows 批处理脚本外，统一使用 LF 换行。
- 代码可读性优先于技巧；不使用晦涩写法换取短代码。
- 业务规则、幂等、状态机、事务、并发控制和安全边界必须能从代码和必要注释中读出原因。
- 不为了“有注释”而写逐行翻译式注释；普通 DTO、简单 getter/setter 和无业务逻辑的配置属性不强制详细注释。

## 4. Java 编码规约

### 4.1 命名

- 类名使用 UpperCamelCase，方法名、参数名、成员变量名使用 lowerCamelCase。
- 常量使用大写下划线命名，集中放在语义明确的常量类、枚举或领域对象中。
- 禁止拼音和英文混用，业务通用名词可以使用约定英文，例如 `order`、`team`、`activity`、`refund`。
- 布尔变量和方法应表达清楚真假语义，例如 `enabled`、`paid`、`canRefund`、`isExpired`。
- 包名按模块边界组织，避免把 `controller`、`mapper`、`redis` 等技术细节泄漏到 `domain`。

### 4.2 代码结构

- 一个类只承担一个清晰职责。
- 方法长度应保持可读；当方法同时处理校验、状态推进、持久化和事件写入时，应按业务步骤抽取私有方法。
- Controller 不写业务规则，Application 不写 SQL 和 Redis 脚本，Domain 不依赖 Spring Web、MyBatis、Redis 或 Controller DTO。
- 枚举必须承载稳定状态值和中文说明；前端展示文案可以独立映射，但后端状态值不能随意变化。

### 4.3 集合、空值和 Optional

- 对外返回集合时优先返回空集合，不返回 `null`。
- 入参必须显式校验，不能依赖下游空指针暴露错误。
- `Optional` 只用于返回值表达“可能不存在”，不作为字段和方法参数。
- 集合遍历中涉及删除、并发修改或状态推进时，必须使用安全写法并补充测试。

### 4.4 异常与错误码

- 业务失败使用项目统一业务异常和错误码，不直接抛出裸 `RuntimeException`。
- 参数错误、身份错误、权限错误、幂等冲突、状态非法、库存不足、系统异常必须区分错误码。
- 异常日志不得输出密码、验证码、token、完整手机号、敏感 payload。
- 捕获异常后必须处理或转换，禁止静默吞掉异常。

### 4.5 日志

- 关键链路日志必须带 `traceId`，交易链路尽量带 `orderId`、`teamId`、`clientOrderNo` 或事件 `bizKey`。
- INFO 记录关键业务结果，WARN 记录可恢复异常，ERROR 记录需要人工关注或任务补偿的异常。
- 日志中避免拼接大对象；必要时输出摘要字段。
- 日志不能替代审计，后台写操作必须写审计记录。

### 4.6 并发、幂等和事务

- 锁单、支付、退款、可靠事件执行都必须有幂等键和重复请求预期行为。
- 涉及金额、名额、状态机推进的写操作必须明确事务边界。
- Redis 只作为缓存和运行态，MySQL 是交易事实源。
- Redis Lua 成功不代表交易成功，MySQL 条件更新和唯一键才是最终兜底。
- 任务 handler 必须可重复执行，失败后可以重试，不能依赖单次执行副作用。

### 4.7 日期、金额和精度

- 金额使用 `BigDecimal` 或以分为单位的整数模型，禁止使用浮点数保存或计算金额。
- 时间字段统一明确时区语义；API 输出使用 OpenAPI 约定的 ISO-8601 字符串。
- 不在业务代码里散落时间格式化字符串，应集中管理时间转换。

### 4.8 数据库和 SQL

- migration 合并后不可修改，只能新增下一版 migration。
- 表字段、索引、唯一键和状态字段必须服务于业务不变量，不只服务查询方便。
- Mapper SQL 涉及条件更新、唯一键冲突、分页、JSON payload 时必须有测试或手工验证证据。
- 禁止使用字符串拼接构造 SQL 条件。
- 批量查询优先避免 N+1。

### 4.9 单元测试和质量门禁

- 高风险业务必须有测试：身份归属、金额、状态机、并发名额、幂等、退款、补偿任务。
- 每个后端任务至少说明执行了哪些测试；无法执行时必须说明原因和替代验证。
- 后续 CI 建立后，Java 代码必须通过 `mvn test`、P3C 或等价静态检查、必要的架构边界测试。

## 5. 编码、换行和格式化规范

### 5.1 文件编码

- 所有源码、Markdown、YAML、JSON、XML、SQL、OpenAPI 文档统一保存为 UTF-8。
- 禁止提交 GBK、ANSI、UTF-8 with BOM 混用导致的乱码文件。
- PowerShell 查看中文文档时优先显式使用 `-Encoding UTF8`，避免终端默认编码造成误判。
- `.editorconfig` 是编辑器默认格式入口；新增 IDE 配置时不得覆盖 `.editorconfig` 的编码、缩进和换行规则。

### 5.2 换行和缩进

- 除 `.bat`、`.cmd` 外，文本文件统一使用 LF 换行。
- Java、SQL、XML 使用 4 空格缩进。
- Markdown、YAML、JSON、TypeScript、Vue、CSS、HTML 使用 2 空格缩进。
- 行尾不得保留多余空格；文件末尾必须保留一个换行。
- 不使用 Tab 缩进。

### 5.3 Maven 和运行时编码

- 后端父 `pom.xml` 必须声明 `project.build.sourceEncoding=UTF-8` 和 `project.reporting.outputEncoding=UTF-8`。
- Maven compiler、surefire、resource 处理不得覆盖为非 UTF-8。
- 运行参数、日志框架和 HTTP 响应默认使用 UTF-8。
- OpenAPI、接口响应和前端请求必须明确 `application/json;charset=UTF-8` 或由框架等价保证。

### 5.4 数据库字符集和时区

- MySQL 数据库、表和文本字段默认使用 `utf8mb4` 字符集。
- 排序规则优先使用 `utf8mb4_0900_ai_ci`；如目标 MySQL 版本不支持，则在 migration 说明中记录替代规则。
- SQL migration 中涉及中文示例数据、错误说明或枚举说明时必须确认 UTF-8 保存。
- 数据库连接必须明确时区策略，避免本地、CI、生产环境时间漂移。

## 6. 注释规范

本项目要求关键代码包含完整、可维护的注释。这里的“完整”指关键意图、边界和风险完整，不是对每一行代码做机械翻译，也不是要求普通 DTO、简单 getter/setter、简单字段映射、无业务逻辑的配置属性都写详细 Javadoc。

### 6.1 注释格式总则

- 承载 public 边界、业务边界、领域规则、外部接口、端口或任务执行逻辑的类、接口、枚举和 public/protected 方法使用 Javadoc：`/** ... */`。
- 普通 DTO、简单 getter/setter、无业务逻辑的配置属性、简单字段映射类不强制详细 Javadoc；字段名和类型已经足够清楚时可以不写。
- public 常量、业务枚举值、关键配置项和影响兜底、安全或审计的配置字段优先使用单行 Javadoc：`/** 说明。 */`。
- 方法内部复杂逻辑使用块注释或行内注释：`// ...`，只解释关键分支和业务原因。
- SQL 文件使用 `--` 写单行注释，复杂 migration 可在文件头使用多行注释说明目的、依赖和回滚注意事项。
- XML、YAML、Markdown 按各自语法写注释，但不得写入敏感信息。

### 6.2 类注释格式

承载业务行为、对外边界或关键扩展点的 public 类、接口和枚举使用以下格式。普通请求/响应 DTO、简单配置属性类和无业务逻辑的字段映射类可以只写一句业务用途，或在命名足够清楚时不写类级详细 Javadoc。

```java
/**
 * 订单锁单用例服务。
 *
 * <p>负责在用户开团或参团时完成价格复核、名额占位、订单落库和可靠事件写入。
 * 调用方必须已经完成登录态解析，用户身份以后端上下文为准。</p>
 *
 * <p>关键约束：Redis 只做前置占位，MySQL 条件更新和唯一键是最终兜底。
 * 本类不直接依赖 Controller DTO。</p>
 *
 * @author zhongxiangpin
 */
public class LockOrderApplicationService {
}
```

### 6.3 方法注释格式

Application 用例入口、Domain 规则/状态机方法、Controller endpoint、Repository port、Scheduler/任务 handler 必须使用以下格式。参数、返回值、异常只保留实际存在的项。普通 getter/setter、简单构造方法、无业务分支的字段转换方法不强制写方法级 Javadoc；字段转换一旦包含默认值、权限裁剪、状态转换、敏感字段处理或兼容逻辑，必须说明原因。

```java
/**
 * 创建待支付订单。
 *
 * <p>该方法会重新执行活动试算，不信任前端传入金额。重复提交相同
 * {@code clientOrderNo} 时返回已有订单，保证用户侧锁单幂等。</p>
 *
 * @param command 锁单命令，用户身份必须来自后端登录上下文
 * @return 锁单结果，包含订单号、队伍号和待支付状态
 * @throws BizException 当活动不可用、名额不足、用户不具备权限或状态非法时抛出
 */
public LockOrderResult lockOrder(LockOrderCommand command) {
}
```

### 6.4 字段、常量和枚举注释格式

- public 常量、业务枚举值、影响运行行为、兜底、安全或审计的配置字段必须写注释。
- DTO 普通字段、私有字段、简单配置属性如果名称已经清楚且无特殊业务含义，可以不写注释。
- 字段注释必须说明业务含义，不重复字段名。

```java
/** 订单支付等待中，允许用户继续支付或超时关闭。 */
WAIT_PAY,

/** 客户端锁单幂等号，同一用户下唯一。 */
private String clientOrderNo;
```

### 6.5 方法内部注释格式

方法内部只在复杂业务处写注释，推荐写在代码块前一行：

```java
// Redis 占位成功只代表拿到临时名额，仍需依赖 MySQL 条件更新做最终兜底。
boolean occupied = teamRuntimeRepository.occupy(command.teamId(), occupyNo);
```

不允许写成：

```java
// 调用占位方法
boolean occupied = teamRuntimeRepository.occupy(command.teamId(), occupyNo);
```

### 6.6 必须写 Javadoc 的位置

- 对外 API、应用用例、领域规则、基础设施端口、任务执行和关键扩展点的 public 类、接口、枚举。
- Application 用例入口方法。
- Domain 领域服务、规则、状态机、策略、值对象中的关键 public 方法。
- Repository port、外部适配 port 和重要 infrastructure 实现。
- Controller endpoint 方法。
- Scheduler、任务 handler、可靠事件 handler。
- 涉及幂等、事务、并发、补偿、Redis/MySQL 兜底、审计和安全边界的类或方法。
- 复杂测试类中表达业务场景的测试方法。

以下位置不强制详细 Javadoc，但命名必须清晰：

- 普通请求/响应 DTO、VO、Command、Result 的简单字段承载类。
- 简单 getter/setter、构造方法、builder 方法。
- 无业务判断的 MapStruct/Bean 拷贝、字段映射、JSON 序列化辅助类。
- 只承载框架绑定的简单配置属性类。

### 6.7 Javadoc 必须说明的内容

按代码职责选择以下内容，不需要机械填满所有项：

- 业务意图：这个类或方法解决什么业务问题。
- 使用边界：由谁调用，不能在哪些场景使用。
- 关键参数：业务含义、可信来源、是否允许为空。
- 返回值：成功结果、幂等重复请求时的结果。
- 异常：可能抛出的业务错误码或非法状态。
- 事务：是否要求调用方或本方法开启事务。
- 幂等：幂等键是什么，重复请求如何处理。
- 并发和兜底：是否依赖 Redis、MySQL 条件更新、唯一键或任务锁，Redis 成功后如何由 MySQL 最终确认。
- 补偿：失败后是否允许重试、如何巡检补偿、是否需要人工处理。
- 安全和审计：是否依赖登录态、管理员权限、审计上下文，安全边界在哪里。

### 6.8 必须写行内或块注释的场景

- 状态机前置条件和状态流转原因。
- Redis Lua、MySQL 条件更新、唯一键兜底等并发控制。
- 补偿、重试、巡检、重建、自动退款等最终一致逻辑。
- 为兼容旧项目或 Harness 行为保留的特殊判断。
- 与直觉不一致但有业务原因的写法。
- 普通 DTO 赋值、简单 getter/setter、显而易见的字段映射不需要行内注释。

### 6.9 不允许的注释

- 不写“设置变量”“调用方法”这类重复代码字面的空注释。
- 不为了满足形式要求给 DTO 字段、getter/setter 或简单映射堆砌空泛 Javadoc。
- 不写过期注释；代码行为改变时必须同步修改注释。
- 不用注释掩盖复杂代码；如果注释很长仍然难懂，优先拆分方法、命名或模型。

## 7. 还必须提前写入的工程问题

以下问题容易在项目中后期放大，后续实现任务必须提前考虑：

- 依赖版本：后端父 POM 和前端包管理必须集中管理版本，禁止随手引入未经说明的新依赖。
- 生成代码：OpenAPI 生成代码必须放在明确目录，不能手改生成物；需要定制时写包装层。
- 配置分层：local、dev、test、prod 配置必须分开，敏感配置只通过环境变量或私有配置注入。
- 密钥和隐私：仓库不得提交真实密钥、token、数据库密码、短信配置和生产域名凭据。
- 日志脱敏：手机号、token、验证码、密码、支付流水敏感片段必须脱敏。
- 国际化和中文：业务错误消息、文档和注释默认中文；接口字段、枚举值、代码标识保持英文。
- 时间基准：定时任务、过期时间、订单倒计时统一明确时区和时钟来源，测试中允许注入 clock。
- ID 生成：订单号、队伍号、支付号、退款号、事件号必须有统一生成策略，避免散落随机字符串。
- 幂等记录：所有外部可重试入口必须说明幂等键、唯一键和重复请求响应。
- 删除策略：交易事实数据默认不物理删除；管理端删除类操作优先做状态禁用或逻辑删除。
- 兼容策略：任何为了兼容旧 Harness 行为的偏差必须写入 Harness 证据或 ADR。
- 可观测性：高风险链路必须预留 traceId、业务 ID、错误码和指标埋点位置。
- 测试数据：seed 数据和 Mock 数据要可重复生成，不依赖手工改库。
- 文件命名：文档、migration、脚本和配置文件使用稳定命名，避免空格和含糊缩写。

## 8. 提交流程中的规范检查

每次后端实现任务提交前，必须自查：

- 是否违反阿里巴巴 Java 开发手册中的强制规约。
- 文件编码、换行、缩进是否符合 `.editorconfig` 和 `.gitattributes`。
- public 边界、Application 用例入口、Domain 规则/状态机、Repository port、Controller endpoint、Scheduler/任务 handler、幂等、事务、并发、补偿、Redis/MySQL 兜底、审计和安全边界是否已有 Javadoc 或必要块注释。
- 普通 DTO、简单 getter/setter 和简单字段映射是否避免了形式化冗余注释。
- 错误码、日志、异常、审计是否符合项目规范。
- 新增 SQL、migration、Mapper 是否有验证证据。
- 是否有无意义注释、过期注释或注释与代码不一致。

PR 或任务总结中必须写明：

```text
开发规范检查：
- 阿里巴巴 Java 开发手册：已检查/不适用，原因：...
- 注释完整性：已检查/不适用，关键注释覆盖：...
- 编码格式：已检查 UTF-8/LF/缩进，或说明不适用原因：...
- 静态扫描：已执行/暂未执行，命令或原因：...
```
