# 业务设计

## 核心链路

```text
注册/登录 -> 多商品会场 -> 商品详情 -> 活动试算
-> 开团/参团 -> 锁单 -> Mock 支付 -> 订单查询
-> 退款/自动退款 -> 管理后台治理
```

## 认证与身份

用户端身份以后端登录态为准。前端不传可信 `userId`，即使请求里保留兼容字段，后端也必须以当前 session 用户为准。

管理员操作必须记录操作者、操作时间、业务对象和操作结果。

## 会场与试算

会场列表展示可用活动、商品、拼团价、统计数据和可参团队伍。

试算服务负责：

- 校验商品和活动是否存在。
- 校验活动时间和状态。
- 计算折扣和实付金额。
- 判断标签人群命中。
- 返回价格快照和活动快照。

## 交易状态机

订单状态：

```text
WAIT_PAY -> PAID -> REFUNDED
WAIT_PAY -> CLOSED_TIMEOUT
```

队伍状态：

```text
PROGRESS -> COMPLETE
PROGRESS -> EXPIRED_UNFORMED
COMPLETE -> COMPLETE_AFTER_REFUND
```

所有状态推进必须有明确前置状态，不能直接无条件更新。

## 锁单设计

锁单使用 Redis + MySQL 双重防超卖：

- Redis Lua 负责高并发名额占位。
- MySQL 更新必须带 `complete_count + lock_count < target_count` 条件兜底。
- 前端传 `clientOrderNo` 作为客户端幂等键。
- 后端生成 `orderId` 和 `teamId`。
- 订单保存活动版本、折扣版本、原价、优惠、实付价和试算时间。

## 支付与退款

第一版使用 Mock 支付，但模型按真实支付扩展设计：

- 支付使用 `payNo` 幂等。
- 退款使用 `refundNo` 幂等。
- 用户退款、管理员退款、过期自动退款需要区分来源。
- 退款记录保存原因、操作者和退款时间。

## 任务治理

任务分为：

- 通知任务。
- 补偿任务。
- 队伍运行态修复任务。

任务 payload 使用结构化 JSON，不手写字符串拼接。任务执行需要执行锁、重试次数、下次执行时间和失败原因。

## 缓存与标签

会场缓存要支持版本失效，避免后台修改活动后用户端长期看到旧数据。

会场列表查询需要批量加载统计和 top teams，避免 N+1 查询。

标签命中优先使用 Redis 或本地缓存，缓存缺失时可以回查 MySQL 明细。

## 管理后台

P0 管理后台提供完整治理能力：

- 订单查询和退款。
- 通知和补偿任务治理。
- 活动配置治理。
- 标签任务治理。
- DCC 配置治理。
- 线程池治理。
- 审计日志查询。
